When 10,000-GPU Training Fails, How Does It Keep Going?

Not with perfect machines: with a fast loop for detecting, fencing, replacing, restoring, and verifying faults.

Gordon Guocheng Qian
July 18, 2026 · 6 min read

Start here: four problems, four responses

01 / SLOW

Straggler

SIGNAL A rank repeatedly trails its group median

ACT Trace compute, network, or input; isolate the suspect

DEFEND Per-step comparisons plus thermal, clock, NVLink, and NIC telemetry

02 / GONE

Hard failure

SIGNAL XID/ECC, device loss, or NCCL timeout

ACT Fence → spare → checkpoint restore

DEFEND RAS/DCGM and targeted diagnostics after suspicion

03 / STUCK

Slow recovery

SIGNAL Restore or rendezvous dominates downtime

ACT Load rank-local shards; read shared state once and broadcast

DEFEND Async sharded checkpoints, meta initialization, spare capacity

04 / WRONG

SDC

SIGNAL NaN, gradient outlier, or shadow replay mismatch

ACT Preserve state; replay, narrow, quarantine, roll back

DEFEND In-fleet tests, shadows, gradient summaries, long checkpoint history

Detect→Fence→Replace→Restore→Verify
Scale check: Llama 3’s 16,384-GPU run saw 419 unexpected interruptions in 54 days—about one every 3.1 hours—and still exceeded 90% effective training time.

1. Stragglers: one slow rank holds everyone up

  • Detect: record every step and collective; compare only with the relevant parallel-group median.
  • Diagnose: decide whether time is spent in compute, communication, or input. Temperature, throttling, PCIe replay, NVLink CRC, and NIC counters point the way.
  • Act: fence persistent outliers before they become a hard failure.

2. Hard failures: fence, replace, restore

  • Trigger: uncorrectable GPU/HBM errors, device loss, missing heartbeat, or an NCCL timeout.
  • Act: stop scheduling the suspect, add a healthy spare, rebuild process groups, and restore from checkpoint.
  • Confirm: use known-answer GEMM, HBM, PCIe/NVLink, and NCCL tests to distinguish GPU, cable, route, and software faults.

Elastic does not mean hot-swapping without a pause. Workers stop, form a new world, then restart from a snapshot.

3. Recovery: checkpoints, loading, and communicators all need to be fast

  • Store: model, optimizer, data position, sampler, and RNG state. Weights alone can restart onto a different training path.
  • Restore: each rank reads only its shard; one worker reads shared state and broadcasts it to peers.
  • Use meta initialization: build the model skeleton without weight bytes, then stream each shard directly to its owning rank.

4. SDC: a matrix multiply can be wrong without failing

  • NaNs: stop propagation, checkpoint more densely, replay, and binary-search the bad set.
  • Finite wrong gradients: before all-reduce, report small summaries such as norm, RMS, and max. Escalate only persistent outliers.
  • Strongest check: a shadow pool replays a sampled step from the same checkpoint and batch. A mismatch implicates both live and shadow groups; it does not instantly identify the guilty one.
  • Hardware layer: Fleetscanner and Ripple use known-answer tests. Hardware Sentinel associates software-failure logs with suspect CPU cores; it is not a GPU-GEMM correctness proof.
Retention: two or three checkpoints protect against a failed write. SDC found days later requires a lower-frequency long history and immutable gold checkpoints.

In one sentence

Find faults early, keep their blast radius small, return quickly, and do not let wrong computation accumulate silently.
